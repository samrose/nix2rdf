# nix2rdf design

nix2rdf turns Nix artifacts into a content-addressed RDF dataset, stores it
in Oxigraph, and reasons over it with Nemo rule packs. This document records
the architecture and every decision in the design brief with its rationale,
including where the implementation deviates and why.

## 1. Mission

One core extractor produces a lossless representation of the Nix derivation
graph. Thin front-ends (flakes, NixOS configurations, OCI images, the
nixpkgs index and full nixpkgs evaluations, Kubernetes clusters) feed that
core. Everything downstream is rules and queries over the graph.

Non-goals for v1: no web UI beyond a one-textarea query page, no incremental
reasoning, no OWL reasoner, no ClickHouse (the fragment layout is columnar-
sink friendly: one file per unit, named by hash), no Layer 1 evaluation by
default, no Kubernetes admission webhook, no cluster mutation.

## 2. Architecture

```
front-ends → core extractor → N-Quads fragments (canonical, zstd, one file per unit)
                                     │
                       ┌─────────────┼────────────────┐
                       ▼             ▼                ▼
                   Oxigraph       Nemo runs      (future sinks)
                  (SPARQL 1.1)   (batch rules)
                       ▲             │
                       └── derived fragments ◄────┘
```

- **Files are canonical.** `store/` holds N-Quads fragments named by identity.
  Oxigraph (`store/oxigraph/`) is a rebuildable index: `nix2rdf rebuild`
  deletes it and reloads every file. Nothing else is load-bearing.
- **SPARQL asks; Nemo derives.** No traversal, closure or classification is
  implemented in Rust. The core pack's ~30 rules are the semantics.
- **Nemo is linked, not shelled out**, in exactly one module
  (`nemo_engine.rs`). It is a vendored, patched copy of upstream commit
  `e578c283` (see `vendor/PATCHES.md`): Oxigraph enables the `sep-0006`
  feature of the shared `spargebra` crate, which adds a `LATERAL` variant
  Nemo's SPARQL import did not match. Two match arms fix it. Upstreaming the
  fix is the exit path from vendoring.
- **Nightly Rust** is required by Nemo (`#![feature]` gates). The date is
  pinned in `rust-toolchain.toml`; the flake reads the same file through
  rust-overlay so `cargo` in `nix develop` and `nix build` agree.

## 3. Identity

See IRI.md. Decisions worth calling out:

- The design brief writes instances as `nix:drv/<hash>`; a prefix cannot map
  to both `…/ns#` and `…/id/`, so instances use `nixid:` (`https://w3id.org/nix/id/`).
- Sources are identified by NAR hash as required. The extractor therefore
  needs `nix path-info` for every `inputSrc`; they are always in the local
  store after evaluation. A missing hash is an error, never a different IRI,
  because the derivation fragment must be byte-identical whoever writes it.
- Content-addressed derivations: the derivation fragment carries
  `nix:contentAddressed true` and no outputs; `nix2rdf attach-outputs`
  writes `out/<drv-hash>` after the build. Input-addressed outputs are in the
  derivation fragment because they are known at evaluation.
- Images: the identity available at build time is the config digest (docker
  image ID). The digest a registry and Kubernetes report is the *manifest*
  digest, which only exists after a push; CI passes it with `--digest` so the
  image node carries the identity `k8s:runsImage` will point at. Both digests
  are stored as `nix:digest` literals.
- Existential nodes from rules get IRIs from the hash of their neighbourhood
  (all triples they appear in, with nulls replaced by a placeholder). Two
  nulls with identical neighbourhoods collapse into one node; they were
  indistinguishable. Result: no blank nodes, derived fragments deterministic.

## 4. Ontology

`ontology/nix.ttl` and `ontology/k8s.ttl`. OWL/RDFS are notation only, stated
in the file header and generated docs. Terms are immutable; deprecation is
`owl:deprecated true` plus a mapping rule. Namespace: `https://w3id.org/nix/`
(unclaimed as of 2026-09-09; registration steps in `w3id/README.md`).
`ONTOLOGY.md` and `ns.html` are generated by `nix2rdf ontology doc` (the
"Widoco or equivalent"), run by `nix build .#ontology-docs`.

Additions beyond the minimum: `Snapshot` (domain of `closureContains`),
`Release`, `PackageVersion`, `Attribute` (Layer 0/1), `OptionValue` (final
value per generation), `Fragment`, and derived-only properties
(`dependsOnTransitively`, `runtimeClosureContains`, `resolvesTo`, `producedBy`,
`sharesLayerWith`). Lossless details the brief did not list: `drvPath`,
`storePath`, `arg` (indexed), `inputDrvOutput`, `envHash`, `structuredAttrs`.

**Environment.** A full derivation environment can be megabytes (structured
attrs, build scripts). The derivation fragment stores `nix:envHash` plus the
well-known keys (`pname`, `version`); `--env full` writes the whole
environment as a side fragment `env/<hash>`. Deviation from strict
losslessness, documented here: the graph is lossless in structure and
recoverable in content with the flag.

**Meta** (`license`, `homepage`, `description`, `sourceProvenance`) depends
on the attribute path used to reach a derivation, so it lives in the snapshot
fragment (pin, nixpkgs revision), never in the derivation fragment.

## 5. Front-ends

All front-ends go through `extract::drv::extract_graph`, which is a pure
function of `NixSource` answers. Two `NixSource`s exist: the Nix CLI and a
recorded-JSON replay used by tests and the sandboxed flake checks.

- **Flake**: lock graph from `nix flake metadata --json` (pins by NAR hash,
  inputs as `(declaring node, name)`, `follows` resolved to the target input),
  installables from `--attr` or `packages.<system>.*`, roots via a
  non-recursive `derivation show`, the whole graph via `-r`. Snapshot = the
  root flake's own pin, typed `nix:Snapshot`, carrying `hasRoot`,
  `closureContains`, per-attribute nodes and meta. `--commit/--repo/
  --committed-at` adds the `Commit` node; timestamps live only there.
- **NixOS**: toplevel closure plus the option tree via one `nix eval --apply`
  expression using builtins only (works on any nixpkgs). Provenance depth is
  final value + `definitionsWithLocations`, no `mkForce`/priority
  reconstruction. Values above 1 KiB of canonical JSON become
  `valueHash` + `values/<hash>` fragments. Default: defined options only;
  `--all-options` for the ~10x larger full tree. Generation identity is the
  toplevel output hash (what `/run/current-system` resolves to), which is
  also what the node annotator module publishes.
- **Image**: builds, then reads the artifact. Docker archives are streamed
  once: each layer tar is hashed while its entries are listed, so
  `layerContains` costs one pass. nix2container JSON is read directly.
  `streamLayeredImage` scripts and OCI directories are not supported in v1.
- **nixpkgs index (Layer 0)**: the three multiverse JSON files → one fragment
  keyed by their content hash. `null` in `versions.json` means "still at the
  tip"; it is stored as `currentAtIndexTip true` plus `lastSeenIn <tip>`.
- **nixpkgs eval (Layer 1)**: `nix-eval-jobs --meta --force-recurse` over an
  expression that imports the tree fetched by `builtins.fetchTree` pinned
  with the index's NAR hash, the same materialization the multiverse `at`
  function performs underneath; `--expr` can substitute the multiverse flake
  itself. Derivation details are read from `.drv` files by default (the
  optional fast path), or in CLI batches with `--reader cli`. The
  determinism test compares both readers.
- **Kubernetes**: manifests (desired) or the API (live) produce plain JSON
  objects; one builder makes the fragments, so both modes share every rule.
  Pods are only used to attribute placement (`scheduledOn`, `replicasOnNode`)
  and pulled digests (`containerStatuses[].imageID`) to their owning
  workload through ReplicaSet/Job owner chains. Secrets are listed as
  metadata only and lose `data` at parse time in manifests mode. Snapshot
  identity is the hash of the normalized fragment content itself, so an
  unchanged cluster produces no new file; the observation time goes in a
  separate `observed/` fragment.

## 6. Evaluation-cost policy

Layer 0 is default and cheap (minutes over all history, no evaluation).
Layer 2 (per consumer commit) is default: `derivation show -r` is seconds,
and derivation fragments already present are not rewritten (`Store::write`
skips existing identities). Layer 1 is explicit and its fragments are
publishable (`nix2rdf publish` / `fetch-fragments` with a hashed manifest).
`evaluatesTo` (could build) and `closureContains` (does depend on) are
distinct predicates.

## 7. Packs and rule runs

Layout and conventions are in PACKS.md. Run semantics:

1. `packs::resolve` orders packs dependencies-first (ties by name);
   `ruleset_hash` = sha256 over (name, version, content hash, rule text).
2. Inputs are fragments: explicit paths, snapshot IRIs (mapped back to
   files by `reason::fragment_for_iri`), `--all-snapshots`, or `--everything`.
   `--input-closure` follows `closureContains`/`hasRoot`/`inputSrc`/
   `runsImage`/`hostGeneration` to their fragments and includes `out/`
   fragments when present. `input_hash` = sha256 over sorted (graph IRI,
   content hash of its N-Quads), so a re-extracted fragment changes the hash.
3. Inputs plus every selected pack's `vocab.ttl` (as `pack:<hash>` graphs,
   so RDFS declarations are facts) are written to a temp N-Quads file; the
   program is prelude + packs + epilogue; Nemo runs in-process; rows of
   `new/3` are collected.
4. The derived fragment is `derived/<ruleset>/<input>`; a separate
   `runs/<ruleset>/<input>` fragment holds the `RuleRun` node with packs,
   inputs, quad count and `ranAt`. Both are loaded.
5. Same inputs + same rules → same file → the run is skipped unless
   `--force`. `gc-derived` drops derived/run fragments of other rulesets.

Packs are meant to be flake inputs of the consumer, so their content hash
in the graph (`nix:usesPack`) answers "which rules produced this fact".

**Admission control has no memory.** A vulnerability feed is just another
input fragment. Loading a new feed changes the input hash of every run that
includes it, so `cve-in-production` re-runs and a workload admitted cleanly
yesterday is flagged today, with the run recorded.

## 8. Storage

See `store.rs` docs and IRI.md. Determinism: quads are sorted by their
N-Quads line, deduplicated, and compressed with zstd level 9 with checksums
off and content size on. The determinism check extracts the fixture twice
into two stores and compares every file byte for byte.

**Volatile data is out of scope.** Metrics, pod state, timings, build
durations belong in columnar storage keyed by these IRIs (a derivation IRI,
a snapshot IRI, a node IRI), not in RDF.

**Disk estimate.** See "Disk estimate" in README.md: ~1 KiB per
derivation on disk, ~200 bytes per quad in the index, Layer 0 for all of
nixpkgs history is 7 MB of fragments; extrapolations for Layer 1 and fleets
are given there.

## 9. Querying

`serve` is a minimal SPARQL 1.1 Protocol endpoint (GET/POST `/query` and
`/sparql`, JSON/CSV/TSV/XML by `Accept`). `query` and `check` run files;
`check` exits non-zero when an ASK is true. QUERIES.md explains why every
shipped query puts its most selective pattern first.

## 10. Engineering

Rust workspace: `nix2rdf-core` (library) + `nix2rdf` (CLI). Static-ish binary
(RocksDB is compiled in; system libs are the C++ runtime and zstd). Logging is
`tracing`, JSON in services (`NIX2RDF_LOG_FORMAT=json`), with the exact Nix
argv and version on every Nix invocation.

Flake `checks`: unit tests (`cargo test`), pack tests (fixture → expected
quads, run by `nix2rdf pack test --all`), determinism (two extractions,
byte compare), e2e on the recorded fixture flake (extract, load, reason,
query, check), Kubernetes snapshot determinism, and ontology validation
(every `.ttl` parses; every `nix:`/`k8s:` term used in Rust or in rules is
declared). Live extraction is not exercised inside the sandbox by design;
`nix2rdf flake --record <dir>` refreshes the fixture from a real run.

## Nix versions and the recorded fixtures

`nix derivation show` changed its JSON schema in Nix 2.34 (top-level
`{"version": 4, "derivations": …}`, store base names instead of paths,
`inputs.{drvs,srcs}`, `structuredAttrs` as an object instead of the `__json`
environment variable, and no `path` for fixed-output outputs). The parser
(`nix::model::parse_derivation_show`) accepts both and normalizes the new
shape to the classic one, re-serializing structured attributes exactly as
Nix does, so a derivation fragment is byte-identical whichever Nix produced
the JSON. That property is what lets independently produced fragments be
shared, and it is verified: `fixtures/hello` was recorded with Nix 2.24,
`fixtures/hello-v4` with Nix 2.34 (the version the binary is wrapped with),
and the `schema-compat` check requires identical `drv/` and `src/` fragments
from both.

The wrapped binary always runs the flake's pinned `pkgs.nix`; that is the
supported version. When the nixpkgs input moves to a Nix with a new schema,
re-record the fixture (`nix2rdf flake … --record fixtures/hello-vN` under
`nix shell nixpkgs#nix`) and extend the check. `nix run .#smoke` runs the
real front-end live for CI runners that have Nix.

## Known limitations

- Runtime `references` require built outputs; without them, runtime closure
  falls back to nothing (not to the build closure), and image `runningClosure`
  falls back to the build closure explicitly in the k8s pack.
- NetworkPolicy reachability covers the ingress side; egress is recorded but
  not folded into `effectiveReachability`.
- Failure-domain spread counts zones from `scheduledOn`, not per-replica
  counts (`replicasOnNode` carries them as literals for SPARQL).
- Version comparison in `host-container-mismatch` is lexicographic.
- Layer 1 for one revision is hours of evaluation and ~1–3 GB of fragments;
  that is why it is opt-in and shareable.
